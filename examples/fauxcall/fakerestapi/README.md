# FakeRESTApi.Web V1: a FauxCall fake

A high-fidelity fake of **FakeRESTApi.Web V1** (https://fakerestapi.azurewebsites.net), generated with
[FauxCall](https://github.com/bradnemetski/fauxcall) from https://fakerestapi.azurewebsites.net/index.html. Agents talk to it exactly
like the real API: same paths, parameters, responses and errors,
consistent data across endpoints, real-world timing, and repeatable state.

## Run it

```bash
uv run fauxcall-fakerestapi            # http://127.0.0.1:8705
uvx fauxcall up fakerestapi            # same, from the workspace root
```

Point your agent at `http://127.0.0.1:8705` instead of
`https://fakerestapi.azurewebsites.net`.

## Control it during evaluations

Every fake has an admin API under `/__fauxcall` (send `X-Fauxcall-Session: <id>` to isolate parallel runs):

| call | what it does |
|---|---|
| `GET /__fauxcall/health` | status, clock, sessions |
| `POST /__fauxcall/reset` | back to the recorded state (`{"session": "..."}` for one session) |
| `POST /__fauxcall/clock` | `{"op": "freeze"}`, `{"op": "travel", "at": "2026-01-05T15:30:00Z"}`, `{"op": "scale", "rate": 60}`, `{"op": "real"}` |
| `GET /__fauxcall/journal` | every call the agent made (filter by `session`, `endpoint`, `since`) |
| `PUT /__fauxcall/faults` | inject errors, timeouts, delays, disconnects, 429s |
| `PUT /__fauxcall/auth/users` | allowed / denied / expired users |

Settings come from `FAUXCALL_*` variables, `.env` and `fauxcall.toml` (e.g. `FAUXCALL_FAST=1` turns off
latency and rate-limit emulation).

## What's inside

| path | what |
|---|---|
| `data/model.json` | everything the fake knows: endpoints, field time policies, relations, errors, jobs |
| `data/recordings/` | the real exchanges it was built from (secrets redacted, personal data pseudonymized) |
| `data/world/` | the consistent dataset it serves |
| `src/fauxcall_fakerestapi/handlers.py` | custom behavior (yours to edit) |
| `src/fauxcall_fakerestapi/routes.py` | one route per real endpoint (regenerated by `fauxcall scaffold`) |
| `tests/` | unit tests, recorded-request replays and end-to-end scenarios (yours to extend) |

## Test it

```bash
uv run pytest                                   # unit + offline end-to-end (no network)
uv run pytest tests/e2e --target=parity         # compare with the real API (needs .env)
```

Endpoints: 27.

### How the real API behaves (and the fake with it)

- All data is generated from fixed rules: 200 books (`publishDate` = now − N days), 30 activities
  (`dueDate` = now + N hours, `completed` = N even), 10 users (`User N` / `PasswordN`), 200 cover
  photos (`idBook` = id). Timestamps follow the fake's clock (`/__fauxcall/clock`).
- **Authors are random on every request** (2–4 per book, numbered in order), on both sides: never
  expect `/Authors/{id}` or `/Authors/authors/books/{idBook}` to repeat between calls (only
  `/Authors/1` and `/Authors/2` are stable).
- **Writes are echoed, never stored.** POST/PUT bind the body like ASP.NET Core + System.Text.Json
  (case-insensitive names, numbers in strings, .NET defaults, the exact error messages with byte
  positions, max depth 32) and echo it; DELETE answers an empty 200 for any int id.
- Route ids bind like .NET's `Int32Converter` (`+5`, ` 1`, `0x10`, `&H1f` work); `v=` API versions
  other than 1.0 in Content-Type/Accept are refused; `Accept: text/json` gets `text/json`.

### Known differences

- `UnsupportedApiVersion` messages name the request URI, so they show the fake's host.
- Error texts for a few malformed bodies were never recorded and follow System.Text.Json's
  resource strings (EOF right after `-`/`.`/`e` in a number, invalid `\u` escapes, raw control
  characters in strings). Bodies declared `charset=utf-32` are assumed to fail like the recorded
  `utf-16` (empty 500). `Uri` fields accept any string (the real API may refuse a few malformed
  absolute URIs).
- `/swagger/v1/swagger.json` is served as `application/json` (real: `application/json;charset=utf-8`);
  the Swagger UI's static assets (`swagger-ui.css`, `*.js`) are not served.
- Parity evidence for writes: every recorded write (≈170, including all error cases) is replayed in
  `tests/unit/test_recorded_writes.py`; one live write-enabled parity run scored 99.98% (its single
  miss was fixed and re-verified live). The real API was approved for at most 20 calls per write
  endpoint; `POST/PUT /Books` and `PUT /Activities` have used all of them, so `test_writes.py`
  avoids those three and should only be run against the real API sparingly
  (`--allow-real-writes`).
